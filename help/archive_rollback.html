工程的归档与回滚

做工程做到一半，最怕的是什么？不是写不出旋律，也不是弹窗画崩了——而是辛辛苦苦干了好几个小时，一不小心把工程文件搞坏了、或者做了一堆试验性的改动全白干。Ctrl+Z 只能后悔几十步，自动保存也只是几分钟前的一个临时版本，万一你把整个工程文件夹都弄乱了，那些工具都救不了你。

所以 Itoc 给了一个更"粗粒度"的后备方案：归档（Archive）和回滚（Rollback）。

📌 本篇的范围：
讲的是工程文件夹层面的归档与回滚：归档会把整个工程文件夹复制一份到"归档库"里保存起来，回滚则用某一份归档覆盖掉当前工程。
如果你要找的是"撤销某一步操作"，请看《撤销与重做》；要找的是"隔几分钟自动保存一份临时文件"，请看《首选项 → 自动保存》相关章节。

一、归档和回滚到底是个啥？

用一句话概括：

💡 归档 = 给整个工程文件夹拍一张快照，存进"归档库"里
回滚 = 挑一张以前的快照，把当前工程整个覆盖成那时候的样子
它不是"撤销某一步"，而是"回到整个工程文件夹的某个历史状态"。

和普通的保存、撤销这些功能最大的区别在于：

  • 它复制的是整个文件夹，不是单个 .czemidi 文件。工程里所有的东西——工程文件本身、audio/ 里的音频、img/ 里的图片、media/ 里的参考媒体、srt/ 里的字幕、UI_Class_Files/ 里的模类——全都会被一起打包复制。
  • 归档是"只增不改"的。你归档多少次，归档库就多出多少份，老的那份不会因为新归档出现就被覆盖掉。
  • 回滚是"破坏性"的。它会把当前工程整个清空，然后再把归档版复制回来。回滚之前，最好先归档一次现场。

所以你可以把归档理解为"手动版本控制"，回滚理解为"切到某个历史版本"。虽然没有 git 那么花哨，但对付日常的工程保护绰绰有余。

二、从哪儿打开？

归档和回滚的入口都在「文件(F)」菜单里：

菜单项位置作用
归档当前工程 文件(F) → 归档当前工程 把当前整个工程文件夹复制一份到归档库
从归档库回滚工程 文件(F) → 从归档库回滚工程（二级菜单） 从归档库里选一个版本，覆盖当前工程

其中，「归档当前工程」是一个普通的菜单项，点了就直接执行；「从归档库回滚工程」是一个二级菜单，鼠标悬停上去会展开一个归档版本列表，你需要先从列表里挑一个。

💡 这两个菜单都需要有打开的工程才能用：
没有打开工程的时候，「归档当前工程」和「从归档库回滚工程」都会提示"请先打开或新建一个工程文件后再归档/回滚"。
原因很简单：归档的前提是知道要归档谁，回滚的前提是知道要覆盖谁。

三、归档当前工程

先讲归档，因为它是回滚的前提（没有归档你回滚个啥）。

3.1 归档时如果工程有未保存的修改怎么办？

这是最容易踩坑的地方，所以放到最前面说。

你的工程在编辑器里改了一堆东西，但没按 Ctrl+S，此时你点「归档当前工程」，Itoc 会弹一个三选一的询问框：

选项行为什么时候选它
是 先自动保存工程，再归档【保存后】的完整工程 你想把现在屏幕上看到的所有改动都存进归档里
否 不保存，直接归档【磁盘上现有】的工程（即未保存前的版本） 你改了但不想保留这些改动，只想存现在磁盘上那份
取消 啥也不干，取消本次归档 你反悔了

三个选项对应的是完全不同的结果，选之前想清楚。

⚠️ 选「否」时最容易踩的坑：
你以为"不保存"= "把现在改的东西也存进归档"？错！
选「否」归档的是磁盘上最后一次保存的版本，你刚才改的那些东西全都没进归档。
如果你想让当前改动进归档，请选「是」。

另外，这里用的是 Itoc 主程序里的"保存工程"逻辑，保存是在后台完成的。选「是」之后，Itoc 会等这次保存真正写盘完成，再开始归档。所以你不会遇到"归档了一半，工程文件还是空的"这种坑。

3.2 归档完放在哪儿？

归档库的位置非常固定，由工程文件的完整路径决定：

  1. 假设你的工程文件是 D:\MyProjects\MySong\MySong.czemidi。
  2. 工程文件所在的文件夹是 D:\MyProjects\MySong\。
  3. 工程文件的父文件夹是 D:\MyProjects\。
  4. 归档库就建在父文件夹下，名字叫 MySong_归档库，完整路径是 D:\MyProjects\MySong_归档库\。

也就是说，归档库和工程文件夹是平级兄弟关系，不是嵌套关系。这样即使你备份、移动、删除工程文件夹，归档库都不受影响。

📌 归档库的名字取决于 .czemidi 文件名，不是工程文件夹名：
比如你的工程文件叫 project.czemidi，放在 D:\MyProjects\MySong\ 里，那归档库会叫 project_归档库，而不是 MySong_归档库。
因为归档库的名字取的是工程文件的文件名（去掉扩展名），不是工程所在的文件夹名。
大部分情况下两者同名所以看不出区别，但如果你的工程文件跟文件夹不同名，就会不一样。

3.3 每次归档会生成什么？

每次归档会在归档库里创建一个新的文件夹，名字是：

{工程文件名}_{时间戳}

其中时间戳的格式是 YYYYMMDD_HHMMSS，比如：

MySong_归档库/
├── MySong_20240115_103045/    ← 1月15日 10:30:45 归档的
├── MySong_20240115_114520/    ← 1月15日 11:45:20 归档的
├── MySong_20240116_090112/    ← 1月16日 09:01:12 归档的
└── MySong_20240116_090112_1/  ← 同一秒内又归档了一次（加了个 _1）

如果同一秒内连续归档了两次，文件名会冲突，Itoc 会自动加 _1、_2 这样的后缀。所以你尽可以连点归档按钮，不会出问题（虽然也没啥意义）。

3.4 归档文件夹里具体有什么？

归档做的事就是把整个工程文件夹原封不动复制一份。所以归档文件夹里的内容和你的工程文件夹里的内容完全一样，所有东西都在：

MySong_20240115_103045/
├── MySong.czemidi          ← 工程文件本身
├── audio/                  ← 音频素材
│   └── bgm.mp3
├── img/                    ← 图片素材
│   ├── icon.ico
│   └── background.png
├── media/                  ← 参考媒体
│   └── reference_video.mp4
├── srt/                    ← 字幕
│   └── lyrics.srt
├── UI_Class_Files/         ← 模类文件
│   └── MyCustomClass.UIclass
└── OfflineMedia/           ← 脱机媒体（如果有）

基本上"工程文件夹里有什么，归档里就有什么"。这也意味着——归档会占用双倍磁盘空间。如果你的工程有几百 MB 的视频素材，那归档一次就多几百 MB。用之前心里有数。

3.5 归档完之后会怎样？

归档成功后：

  1. Itoc 会在界面上弹一个轮播图通知，告诉你"工程已归档: MySong_20240115_103045"。
  2. 如果轮播图不可用，会弹一个普通的对话框显示归档成功的信息（包含归档库路径和具体的子文件夹名）。
  3. 程序会自动打开归档库所在的文件夹（用系统文件管理器），方便你马上看到归档成果。

这一步是为了让你有"确实做完了"的实感。毕竟归档是一个危险操作（回滚的时候要以它为准），看到文件真的躺在那儿，你才放心。

💡 归档前的心理准备：
归档本身完全不会动你当前的工程文件夹。它只是复制一份出去。所以你完全不用担心归档会把现有东西搞坏。
反过来说，如果归档失败（比如磁盘满了），当前工程也不会受影响，你只是少了一份新归档而已。

四、从归档库回滚工程

现在是重头戏了。回滚是个破坏性操作，用之前一定要看清楚。

4.1 二级菜单长什么样？

鼠标悬停在「文件(F)」→「从归档库回滚工程」上，会展开一个二级菜单。这个菜单是每次弹出前动态生成的，内容实时反映归档库里现在有多少个版本。

菜单结构大概是这样：

┌──────────────────────────────────────────────┐
│  ─ 选择要回滚的归档版本 ─                     │
│  1. MySong_20240116_090112                    │
│  2. MySong_20240115_114520                    │
│  3. MySong_20240115_103045                    │
│  ──────────────────────────                  │
│  打开归档库文件夹                             │
└──────────────────────────────────────────────┘

说明几点：

  • 按时间从新到旧排列。最上面的是最新归档，最下面的是最老归档。这和 git log 的习惯一样，越新的越容易点。
  • 只显示文件夹，不显示里面的文件。菜单里列的都是 MySong_时间戳 这种名字，一眼就能看出是什么时候归档的。
  • 最底下的「打开归档库文件夹」，点了直接弹出文件管理器打开归档库。如果你只是想看看归档库里有啥，不要回滚，用这个。
  • 归档库为空时，菜单里会显示一行灰掉的「（暂无归档）」，点不了。
  • 没有打开工程时，整个「从归档库回滚工程」压根弹不出来（前置检查直接拦下）。

4.2 选了一个归档后，会看到什么？

点下去之后，会弹一个二次确认对话框。别嫌它烦，这真的是保护你的最后一道关卡。对话框内容大概是这样：

确认回滚

即将用归档版本覆盖当前工程:

  归档: MySong_20240115_103045
  当前工程: MySong.czemidi

⚠ 当前工程的所有文件将被归档版本覆盖！
建议先「归档当前工程」保留现场，再执行回滚。

确定要继续吗？

看清楚这三段：

  1. 归档：告诉你待会儿会拿哪一份归档来覆盖。确认是不是你想回滚到的那个时间点。
  2. 当前工程：显示你当前正在用的工程文件名。确认你回滚的不是别的工程。
  3. ⚠ 警告语：再次提醒你"当前工程的所有文件都会被覆盖"。
⚠️ 强烈建议在回滚之前先归档一次！
万一你回滚完发现"卧槽还不如原来呢"，你手里就没有后悔药了——因为回滚是覆盖式的，旧内容已经被删了。
正确姿势：先点「归档当前工程」，再点「从归档库回滚工程」。这样即使回滚错了，你还能再回滚回来。
归档是"非破坏性"的，所以多归档一次没有任何成本（除了磁盘空间）。

4.3 回滚流程详解

点了"确定"之后，Itoc 做了一长串事情。这里按执行顺序一步步讲，方便你理解"为什么回滚有时候看着慢"。

4.3.1 第一步：停止播放并释放音频占用

这一步非常重要，也是最容易出问题的地方。

先说问题：Itoc 在播放音频的时候，会一直占用着音频文件（尤其是 mp3）。你如果正在播放 audio/bgm.mp3，Windows 是不允许删除这个文件的。同理，整个 audio/ 文件夹也删不掉。

而回滚需要先"清空当前工程文件夹"，如果音频文件删不掉，整个回滚就失败了。

所以回滚的第一步就是：

  1. 如果正在播放，先把播放停掉。
  2. 再把音频文件彻底释放，让系统真正放手。

这样文件占用就解除了，后面删文件夹才不会报错。

💡 为什么有时候回滚会卡个一两秒？
就是这个环节。音频文件的占用不是一瞬间就能放掉的，有时候 Windows 需要几十到几百毫秒才真正松手，程序会在这里停一下，给系统一点时间。

4.3.2 第二步：关闭当前工程

程序会把当前工程关掉。

注意：这一步不会问你"要不要保存"，因为回滚本来就要把当前工程丢掉，问了也白问（而且上一环节已经问过要不要先归档了）。

这一步会清空内存里的所有工程数据：音符、全局命令、标记、便利贴、音频路径、以及 UI 上的所有面板。

4.3.3 第三步：清空当前工程文件夹

这一步就是真的动磁盘了：遍历工程文件夹里的所有文件和子文件夹，逐个删除。

程序在这里带了重试机制：最多尝试 3 次，每次失败后等半秒再试。这是为了对付 Windows 的"文件占用残留"问题——有时候文件占用的记录清掉了，但系统还没完全放手，直接删会报错，等半秒再删就好了。

📌 如果 3 次都删不掉怎么办？
程序不会弹窗报错。它会带着残留文件继续往下走，因为下一步是"把归档内容复制回来并合并"，目标文件夹里已经有东西也不会中断。
残留的旧文件如果跟归档里的新文件同名，会被覆盖掉；如果不同名，会留在原地。所以理论上回滚后工程文件夹里可能混着几个删不掉的旧文件——通常不影响使用，但你看到的时候别慌。

4.3.4 第四步：把归档内容复制回工程文件夹

把归档文件夹里的所有内容复制回工程文件夹。

"已存在就合并"这个行为很关键——目标文件夹里已经有东西时不报错，而是合并进去。这样即使上一步有残留文件，复制也不会中断。

复制过程中，如果某个文件因为种种原因复制失败（比如又遇到文件占用），程序会记下这次失败继续往下走，不会中断整个流程。

4.3.5 第五步：重新打开工程

复制完之后，程序会把工程重新加载回来。

这里有个小细节：程序不是直接拿原工程路径去打开的，而是先检查原路径还在不在：

  • 在的话，直接打开。
  • 不在的话（比如归档里 .czemidi 文件名变了），去工程文件夹里找一个 .czemidi 文件，用它打开。
  • 连 .czemidi 文件都找不到，弹一个警告："文件已回滚，但未找到 .czemidi 工程文件，请手动打开。"

正常情况下最后一步用不上，但谁让你手欠删过工程文件呢。

4.3.6 完成：弹通知

回滚成功后，跟归档一样会弹一个轮播图通知："工程已回滚: MySong_20240115_103045"。

到这，整个回滚就结束了。你会发现：

  • 工程文件、音频、图片、模类、字幕……全都回到了那个时间点的样子。
  • 你刚才改的东西全没了（除非你回滚前归档过）。
  • 界面会自动重新加载工程，可能还会顺带重建侧边栏、刷新当前选中状态。

4.4 一个"坑爹"的边界情况：工程在归档库里

程序里有一层保护：如果当前工程就在归档库内部（比如你手贱打开了 MySong_归档库/MySong_20240115_103045/MySong.czemidi），那回滚会直接拒绝。

弹窗内容大概是：

回滚失败
当前工程位于归档库内部，无法回滚。

为什么？因为回滚的逻辑是"清空当前工程文件夹 + 复制归档内容回来"。如果当前工程就在归档库里，清空"当前工程文件夹"就等于把归档本身删掉了——这波操作下来数据全灭。

所以程序里加了一层判断：只要当前工程文件夹落在归档库里面（或者干脆就是归档库本身），就直接拒绝回滚。

💡 什么时候会踩到这个坑？
最常见的情况是：你手动去归档库文件夹里双击打开了一个 .czemidi 文件，然后顺手在这个"归档版工程"上继续编辑、想回滚。
解决办法：不要直接在归档库文件夹里编辑工程。归档就是"快照"，你应该把它当只读的看。要恢复某个版本，用「从归档库回滚工程」这个正规入口。

五、归档库长啥样？（可视化）

假设你的工程在 D:\MyProjects\MySong\ 里，叫 MySong.czemidi。归档了几次之后，文件夹结构是这样：

D:\MyProjects\
├── MySong\                          ← 当前工程文件夹
│   ├── MySong.czemidi
│   ├── audio\
│   ├── img\
│   └── ...
│
└── MySong_归档库\                    ← 归档库（跟工程文件夹平级）
    ├── MySong_20240115_103045\      ← 第 1 次归档
    │   ├── MySong.czemidi
    │   ├── audio\
    │   ├── img\
    │   └── ...
    ├── MySong_20240115_114520\      ← 第 2 次归档
    │   └── ...（同样结构）
    └── MySong_20240116_090112\      ← 第 3 次归档
        └── ...（同样结构）

你看，归档库就是个"文件夹套文件夹"，每一个子文件夹都是一份完整的工程快照。

归档库里的文件夹不是 Itoc 内部格式，就是普通的 Windows 文件夹。你可以用文件管理器直接进去看，可以直接拷贝走，可以打包 zip，也可以手动删掉不想留的归档（通过「从归档库回滚工程」菜单看不到被删的，因为菜单是实时扫描文件夹的）。

📌 归档库可以手动清理：
归档库不会自动清理。你归档了多少次，它就留着多少份。如果你工程有 200MB，归档 10 次就是 2GB。
手动删掉不需要的归档文件夹是安全的——只要你不删"当前正在回滚的那一刻还在用的"那一个。删完之后菜单下次打开就会少掉对应条目。

六、归档 vs 撤销 vs 自动保存 vs 手动保存

这四件事经常被搞混，用一张表对比清楚：

能力 撤销 / 重做
（Ctrl+Z / Ctrl+Shift+Z）		 自动保存 手动保存
（Ctrl+S）		 归档 / 回滚
粒度 单个操作 整个工程 整个工程 整个工程文件夹
覆盖范围 仅 .czemidi 内存数据 仅 .czemidi 文件 仅 .czemidi 文件 所有素材文件（音频/图片/模类/字幕……）
历史保留 最近 N 步（默认 30） 最近 N 个临时文件 不保留（只有一个当前版本） 全部保留（需手动清理）
触发方式 自动记录 定时触发 手动 手动
会丢失素材吗 不会 不会 不会 会覆盖素材
适用场景 改错了想撤回 程序崩溃兜底 阶段性成果 重大试验前的备份

简单说：

  • Ctrl+Z = 一步悔棋。
  • 自动保存 = 程序崩了别让你白干。
  • Ctrl+S = 阶段性落实。
  • 归档 = 给整个工程文件夹拍一张"纪念照"。想回到某个阶段，就用 回滚 挑那张照片回来。

七、常见问题

Q1：归档之后，我发现归档的是个错误的版本，能删掉吗？

能。直接去归档库文件夹里删掉对应的子文件夹就行。删完之后在 Itoc 里重新打开「文件(F) → 从归档库回滚工程」菜单，那个条目就没了哦。

Itoc 里没有"删除归档"的 UI 按钮，因为归档库就是普通文件夹，用文件管理器删更顺手。

Q2：归档会占用多少磁盘空间？

跟你工程文件夹本身一样大。归档多少次就占多少倍。

比如你的工程文件夹里有 bgm.mp3 10MB、reference_video.mp4 50MB、一堆图片 20MB，那工程文件夹本身大概 80MB 左右。归档一次就多 80MB。归档 10 次就 800MB。

所以如果工程很大，记得定期手动清理归档库呀。

Q3：为什么不自动清理老的归档？

因为归档是保底用的。有些人专门留着一个"我上个月写的完美版本"做参照，自动清理可能会把那个版本误删掉。所以留给用户自己控制。

Q4：回滚的时候，当前工程的音乐一直在放，怎么办？

回滚的第一步就是停止播放、释放音频文件的占用，所以你会听到音乐突然停掉，这是正常的。

如果音乐没停就报错，说明停止播放这一步本身出了状况（极少数情况），这时候回滚可能会失败。解决办法：手动点一下主界面的停止按钮，或者结束当前播放，再重新尝试回滚。

Q5：回滚失败了怎么办？当前工程是不是废了？

不一定。回滚流程的执行顺序是：先停播放 → 再关工程 → 再删文件 → 再复制归档。

如果失败发生在"复制归档"阶段之前（停播放、关工程、删文件），那当前工程确实可能被删了一部分。但！只要归档文件本身是完好的，你直接手动去归档库文件夹里，把那个子文件夹整个复制粘贴回工程位置就行——这跟回滚做的是同一件事，只是手动。

如果失败发生在"复制归档"阶段，那工程文件夹里可能是新旧混杂的状态。这时候建议：

  1. 先把当前工程文件夹整个挪走（MySong_坏掉的）保底。
  2. 从归档库文件夹里，手动把归档子文件夹的内容复制到新工程位置。
  3. 手动打开 .czemidi 文件。

Q6：归档当前工程和「另存为工程副本」有什么区别？

区别挺大：

  • 归档当前工程：复制到固定的归档库位置（工程文件夹的父目录下），命名带时间戳，不会打开复制出来的工程，只负责备份。
  • 另存为工程副本：保存到你指定的任意位置，作为一份可携带的副本。会把路径处理成相对路径，方便发给别人或者换电脑打开。

前者是"给自己留备份"，后者是"给别人传副本"。目的完全不同。(๓´˘`๓)

Q7：归档成功后自动弹出的那个"文件管理器窗口"，我能关掉吗？

能，那只是个普通的系统文件管理器窗口，关掉完全不影响 Itoc。

如果你觉得每次归档都弹窗口很烦——对不起，这个行为是写死的，关不掉。不过你可以归档完之后直接 Alt+F4 关掉它。

Q8：我不小心把归档库文件夹删了怎么办？

那就没归档了呗。不过当前工程本身不受影响，因为归档库和工程文件夹是平级的，删归档库不会动工程。

你可以重新建一个"工程名_归档库"文件夹，但里面的历史归档已经没了，只能从现在开始重新归档。

Q9：归档时提示"当前工程位于归档库内部，无法回滚"，但我明明是从自己的工程文件夹打开的？

这说明"当前工程文件夹"和"归档库"的路径有前缀关系，程序判定你已经在归档库内部了。

最常见的情况是：你的工程文件夹本身名字就叫 xxx_归档库，或者你手动把工程挪进了归档库文件夹。检查一下当前工程文件的完整路径，看看是不是这种情况。

解决办法：把工程文件夹挪到归档库外面，或者重新新建一个工程。

Q10：回滚的时候，如果某个归档文件夹损坏了，会怎么样？

回滚只认归档文件夹的路径和里面的普通文件，只要文件夹还在、里面有文件，就能复制。它不会去"验证"归档里的 .czemidi 是不是合法 JSON。

所以如果归档里的 .czemidi 损坏了，回滚过程中不会有任何提示，但最后打开工程那一步会报错（"加载工程文件失败"或类似的）。这时候你只能从归档库的其他版本里找一个完好的，或者手动修。

八、小结

「归档与回滚」是 Itoc 里粒度最粗、但保护力度最强的版本管理工具。

  • 归档：把整个工程文件夹复制到 工程名_归档库/ 下，生成一份带时间戳的快照。
  • 回滚：从归档库里挑一份，覆盖当前工程文件夹（破坏性操作）。
  • 入口在「文件(F)」菜单里，归档是普通菜单项，回滚是二级菜单。
  • 归档前如果有未保存修改，会弹三选一（是 / 否 / 取消）。选"是"才是"保存后归档"。
  • 归档库与工程文件夹平级，不嵌套。归档库名由 .czemidi 文件名决定，不由工程文件夹名决定。
  • 回滚前强烈建议先归档一次，保留现场，否则回滚错了无法挽回。
  • 回滚会自动停播放、释放音频占用、关工程、清空文件夹、复制归档回来、重新打开工程。
  • 回滚成功后会有轮播图通知，工程状态会完全回到归档时的样子。
  • 归档库不会自动清理，占用的磁盘空间等于工程文件夹大小 × 归档次数。
  • 归档库就是普通文件夹，可以手动删、手动挪、手动管理。

记住：归档和回滚是"整个文件夹级别"的后悔药，比撤销狠得多，也比撤销慢得多。用它之前，先归档一次保底，再放心地折腾。
