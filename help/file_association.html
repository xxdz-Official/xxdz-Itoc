🔗 文件关联（打开方式）

你有没有过这种体验：下载了一个 .czemidi 工程文件，双击它，结果系统弹出来一个"选择打开方式"的窗口，或者干脆用记事本把一堆 JSON 文本给你铺满屏幕……

这就是"没做文件关联"的表现。文件关联做好了，双击 .czemidi 就能直接用 Itoc 打开，双击 .UIclass 就能直接进模类设计器，双击 .CzeData 就能直接用解释器跑——省心省事。

📌 这篇唠的是啥：
首选项里「打开方式」这一块的完整说明：三种扩展名分别关联到什么、怎么绑定、怎么解绑、状态怎么看、以及 Windows 默认应用保护的坑怎么绕。
关于首选项窗口的其它分类，请参考《首选项（设置）》文档。

一、从哪儿打开？

菜单 「文件(F)」→「首选项」→ 左侧「打开方式」分类。

二、三种文件类型

Itoc 支持三种自定义文件扩展名，每种都有自己的启动器：

扩展名文件类型双击后打开什么对应启动器
.czemidi Itoc 工程文件 用 Itoc 打开这个工程 launcher/OpenCZEmidiFile.exe
.UIclass Itoc 模类文件 用模类设计器打开 launcher/OpenUIclassFile.exe
.CzeData 解释器数据中转文件 用配置好的解释器打开 launcher/OpenCzeDataFile.exe
💡 为什么用启动器而不是直接关联主程序？
因为 Itoc 主程序（main.py 或 Itoc.exe）是"编辑器"，而双击文件需要的是"打开文件"这个动作。
启动器就是专门干这个的：接收一个文件路径，然后把 Itoc 拉起来，告诉它"打开这个文件"。
这样主程序的启动逻辑和"打开文件"的逻辑就解耦了，更干净。

2.1 启动器是用 C++ 写的

三个启动器都是独立的 C++ 小程序，各自对应一个 .cpp 源文件，编译出来就是 launcher/ 文件夹里的 exe。

启动器 exe对应源码作用
OpenCZEmidiFile.exe main主程序启动器.cpp 接收 .czemidi 路径，拉起 Itoc 主程序
OpenUIclassFile.exe main模类启动器.cpp 接收 .UIclass 路径，拉起模类设计器
OpenCzeDataFile.exe OpenCzeDataFile.cpp 接收 .CzeData 路径，拉起配置好的解释器

为什么用 C++ 写？因为这个启动器要做的事很简单——拿到文件路径、写个小 JSON、拉起主程序，用 C++ 编译出来体积小、启动快、不依赖 Python 环境。你用 .czemidi 双击打开的时候，是 .exe 在干活，不需要本机装 Python。

2.2 启动器的通用工作流程

三个启动器的行为大同小异，都是这三步：

  1. 读取命令行参数：双击文件时，Windows 会把文件路径作为 argv[1] 传给启动器。
  2. 写一个 JSON 信号文件：把文件路径写到一个约定的 JSON 里，告诉主程序"我要打开这个文件"。因为路径里可能有中文，启动器会先把 ANSI 转成 UTF-8 再写。
  3. 按优先级启动主程序：优先找编译好的 .exe，找不到再回退到 .py，用 pythonw.exe 或 python.exe 拉起来。

主程序启动后会去读那个 JSON，发现有文件路径就自动打开——这就是"双击文件直接进 Itoc"的完整链路。

2.3 三种启动器的区别

① OpenCZEmidiFile.exe（工程启动器）

  • 写信号文件到：launcher/RunData/launch_info.json
  • 启动目标优先级：Itoc.exe → main.py（用 pythonw.exe / python.exe）
  • 用 CreateProcessA 启动 exe，用 ShellExecuteA 启动 py

② OpenUIclassFile.exe（模类启动器）

  • 写信号文件到：launcher/RunData/open_uiclass_info.json
  • 启动目标优先级：UI_Class.exe → UI_Class.py（用 pythonw.exe / python.exe）

③ OpenCzeDataFile.exe（解释器启动器）

  • 写信号文件到：runCZE/temp/launch_info.json
  • 启动目标优先级：
    1. shezhi.txt 里配置的 test_interpreter_path
    2. runCZE/runCZEx64.exe（固定默认解释器）
    3. runCZE/runCZE.py（用 pythonw.exe / python.exe）
  • 注意：这个启动器不读 interpreter_* 和 current_interpreter_mode 字段，避免用户误把主解释器指向别的 exe 时被 .CzeData 误触发
📌 启动器出问题怎么办？
每个启动器都会在自己所在的目录下生成一份日志：
· launcher/launcher_log.txt（工程和模类启动器）
· launcher/interpreter_launcher_log.txt（解释器启动器）
日志里记录了参数、文件路径、启动目标、错误码等等。双击没反应的时候，先去看日志。

3.1 启动器路径

每个文件类型下面都会显示对应的启动器完整路径。路径是只读的，不能改，因为它固定指向 launcher/ 文件夹下的某个 exe。

如果某个启动器不存在，点绑定时会提示"找不到启动器文件"。

3.2 绑定 / 解绑按钮

按钮作用
绑定 把对应扩展名关联到启动器。写注册表，只影响当前用户，不影响系统全局
解绑 删除注册表里所有相关的关联项，恢复"未关联"状态

3.3 状态提示

窗口最下方有一块状态区，会同时显示三种扩展名的关联状态。颜色代表状态：

图标颜色含义
✅绿色已关联到正确的启动器（就是 Itoc 的）
⚠️橙色已关联到其它程序（比如被别的软件抢走了）
❌红色未关联

点「刷新状态」会重新检测一遍。

四、怎么绑定？

以 .czemidi 为例：

  1. 确认 launcher/OpenCZEmidiFile.exe 文件存在（启动器路径那行会显示）
  2. 点 「绑定 .czemidi 到 OpenCZEmidiFile.exe」
  3. 如果启动器不存在，会弹错误框；存在则写入注册表
  4. 写完后自动刷新状态，会看到状态变成 ✅

4.1 注册表里写了什么？

绑定会在当前用户注册表（HKEY_CURRENT_USER）里创建这些项：

HKCU\Software\Classes\Itoc.CzeMidi\
    (默认值) = "Itoc 工程文件"

HKCU\Software\Classes\Itoc.CzeMidi\DefaultIcon\
    (默认值) = "启动器完整路径,0"

HKCU\Software\Classes\Itoc.CzeMidi\shell\open\command\
    (默认值) = "启动器完整路径" "%1"

HKCU\Software\Classes\.czemidi\
    (默认值) = "Itoc.CzeMidi"
    Content Type = "application/x-itoc-czemidi"

简单说就是三件事：

  1. 注册一个"程序 ID"（ProgID），告诉系统这个类型叫什么、用什么图标、用什么命令打开
  2. 把扩展名 .czemidi 指向这个 ProgID
  3. 通知系统刷新（SHChangeNotify）
💡 为什么用 HKCU 而不是 HKLM？
HKCU 是"当前用户"，写它不需要管理员权限；HKLM 是"系统全局"，写它需要管理员权限。
Itoc 的文件关联只影响你自己，所以用 HKCU 就够了，也不用弹 UAC。
好处是你怎么折腾都不会影响别人的账号。

五、怎么解绑？

点对应类型的 「解绑」按钮，会删掉这些注册表项：

HKCU\Software\Classes\.czemidi\
HKCU\Software\Classes\Itoc.CzeMidi\
HKCU\Software\Classes\Applications\OpenCZEmidiFile.exe\
HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\FileExts\.czemidi\

删完之后，.czemidi 就恢复到"未关联"状态了，双击会弹 Windows 的"选择打开方式"。

5.1 为什么解绑有时"不彻底"？

因为最后一项 FileExts\.czemidi 里的 UserChoice 子项受 Windows 保护，脚本删不掉。

UserChoice 记录的是"用户最后一次手动选择的默认程序"。比如你曾经手动把 .czemidi 设成用记事本打开，这个选择就记在 UserChoice 里。系统会优先认 UserChoice，注册表里的其它关联都要让位。

⚠️ 想彻底解绑，需要手动操作：
1. 按 Win+I 打开「设置」
2. 进入「应用」→「默认应用」
3. 滑到最下面，点「按文件类型选择默认应用」
4. 找到 .czemidi，把它改成别的程序（比如记事本）
5. 或者直接在列表里找到 .czemidi，右键 →「删除」
这样 UserChoice 就被清掉了，解绑才算彻底完成。

六、Windows 默认应用保护的坑

这是很多人会遇到、而且容易踩的坑：绑定了，但双击文件还是不用 Itoc 打开。

6.1 为什么会这样？

Windows 8 之后，微软为了"防止流氓软件劫持文件关联"，给默认应用加了一层保护。具体规则：

  • 注册表里的 HKCU\Software\Classes\.xxx 只是"候选关联"
  • 系统实际用的是 UserChoice 里的记录
  • UserChoice 只有用户手动确认才能被写，脚本改不了

所以光写注册表没用，还得让用户手动确认一次"就用这个程序"。这本质上是微软的"防劫持"设计，是好事。

6.2 怎么绕过？

不能绕过（这是好事）。但你可以手动确认一次，之后系统就认了。步骤：

  1. 找到任意一个 .czemidi 文件
  2. 右键它 →「打开方式」→「选择其他应用」
  3. 在弹出窗口里点「更多应用」→「在这台电脑上查找其他应用」
  4. 浏览到 launcher\OpenCZEmidiFile.exe，选中它
  5. 勾上底部的「始终使用此应用打开 .czemidi 文件」
  6. 点确定

这一步做完，UserChoice 就被写进去了。之后双击 .czemidi 就会用 Itoc 打开。

💡 那"绑定"按钮还有什么用？
有用。绑定按钮做了两件事：
1. 写好 ProgID 和图标，让"选择打开方式"窗口里能看到 Itoc 的图标和名字
2. 写好 HKCU\Software\Classes\.czemidi，作为"候选关联"
这样你在"选择其他应用"列表里就能一眼找到 Itoc，不用手动去文件系统里翻 exe。
绑定 + 手动确认一次 = 完整流程。

七、状态检测原理

状态提示是怎么判断的？其实就是读注册表：

  1. 打开 HKCU\Software\Classes\.czemidi，读出它的默认值（ProgID）
  2. 打开 HKCU\Software\Classes\{ProgID}\shell\open\command，读出命令行
  3. 看看命令行里有没有包含 Itoc 的启动器路径

结果分三种：

情况显示
命令行里包含 Itoc 启动器路径✅ 已关联到: 启动器路径
命令行存在但不包含 Itoc 路径⚠️ 已关联到其他程序: 具体命令行
注册表项不存在❌ 未关联

注意：状态检测不看 UserChoice，只看 HKCU\Software\Classes。所以可能出现"状态显示 ✅，但双击还是用别的程序打开"这种情况——这时候就是 UserChoice 在起作用，按 6.2 节手动确认一次就好。

八、常见问题

Q1：绑定的时候提示"找不到启动器文件"？

说明 launcher/OpenCZEmidiFile.exe 不存在。检查一下：

  • Itoc 安装目录下有没有 launcher/ 文件夹
  • 文件夹里有没有对应的 exe 文件
  • 文件名有没有被改过

如果文件确实丢了，重新下载完整版的 Itoc。

Q2：绑定了，双击还是弹"选择打开方式"？

说明 UserChoice 还没建立。按 6.2 节手动确认一次即可。

Q3：绑定了，双击结果用记事本打开？

说明 UserChoice 里记录的是"用记事本打开"。按 6.2 节手动改成 Itoc 启动器。

Q4：解绑之后还是双击用 Itoc 打开？

也是 UserChoice 的锅。解绑删的是注册表关联项，但 UserChoice 删不掉。按 5.1 节手动去设置里改。

Q5：改了默认程序之后，Itoc 的图标没了？

图标是绑定时写到 DefaultIcon 里的。如果被别的程序覆盖了，重新点一下「绑定」，图标就回来了。

Q6：三种文件类型要不要都绑？

看你需求：

  • .czemidi：做工程的肯定要绑，天天用
  • .UIclass：如果你经常做模类，绑上方便
  • .CzeData：如果你经常直接跑 CzeData 文件，绑上方便

反正绑了不碍事，全绑上也行。

Q7：绑定会不会影响别的软件？

不会。HKCU 是当前用户的注册表，只影响你自己的账号。其它用户、系统级别的关联都不受影响。

而且 .czemidi / .UIclass / .CzeData 这三个扩展名本来就是 Itoc 自定义的，一般不会有别的软件来抢。

Q8：绑定的信息存在哪？

存在 Windows 注册表的 HKEY_CURRENT_USER\Software\Classes\ 下面。这是 Windows 标准做法，所有软件的文件关联都写在这。

卸载 Itoc 的时候，如果安装程序没自动清，可以手动用「解绑」按钮清掉，不留垃圾。

Q9：能用命令行绑定吗？

当前版本没提供命令行绑定入口，只能通过首选项的按钮。如果你有批处理需求，可以自己写 reg 文件导入。

Q10：为什么绑定需要"手动确认"这一步？烦不烦啊？

烦是烦，但这是微软为了"防止恶意软件偷偷改默认程序"的设计。

想象一下，如果任何软件都能随便改默认浏览器、默认看图工具、默认音乐播放器——那就乱套了。所以微软在 Windows 8 之后加了 UserChoice 保护，必须用户手动点头才认。

对用户来说是"多一步确认"，但对系统安全来说是"多一层保险"。Itoc 尊重这个设计，所以只做"绑定到候选关联"，不尝试绕过它。

Q11：启动器日志在哪？双击没反应怎么排查？

每个启动器都会在同目录下写日志：

启动器日志文件
OpenCZEmidiFile.exelauncher/launcher_log.txt
OpenUIclassFile.exelauncher/launcher_log.txt
OpenCzeDataFile.exelauncher/interpreter_launcher_log.txt

日志是 UTF-8 编码（带 BOM），用记事本直接打开就能看。里面记录了：

  • 启动器启动时间
  • 收到的命令行参数（也就是文件路径）
  • 写信号文件的路径和结果
  • 尝试启动的目标 exe / py 路径
  • 启动成功或失败的状态、错误码

双击没反应时，第一件事就是去看日志，通常一眼就能看出问题在哪。

Q12：启动器是用什么写的？能不能自己改？

三个启动器都是用 C++ 写的（Windows API，不依赖任何第三方库）：

  • main主程序启动器.cpp → 编译出 OpenCZEmidiFile.exe
  • main模类启动器.cpp → 编译出 OpenUIclassFile.exe
  • OpenCzeDataFile.cpp → 编译出 OpenCzeDataFile.exe

九、小结

「文件关联（打开方式）」管的是"双击某类文件时用哪个程序打开"。关键记住这几条：

  • 位置：文件(F) → 首选项 → 打开方式
  • 三种类型：.czemidi（工程）、.UIclass（模类）、.CzeData（解释器数据）
  • 启动器是 C++ 写的：体积小、启动快、不依赖 Python 环境
  • 绑定：写 HKCU 注册表，把扩展名关联到启动器
  • 解绑：删注册表项，恢复"未关联"
  • 状态检测：读注册表看命令行里有没有 Itoc 启动器路径
  • Windows 保护：注册表写完还要手动确认一次，双击才生效
  • 排查问题：先看 launcher/ 下的日志文件
  • 不影响别人：只用 HKCU，不用管理员权限，不碰系统全局

绑一次，省一辈子事。绑完之后双击 .czemidi 就能直接进 Itoc，比"打开软件 → 文件 → 打开工程"快多了。
